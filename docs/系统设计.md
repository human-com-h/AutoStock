## 0. 文档说明

本文是《系统概要》的下一层落地设计，概要里已确定的目标、功能清单、技术栈、阶段规划全部保留不变。设计过程中有几处概要未展开、但不定就无法编码的点，在此统一说明，后文出现时会再次标注。

### 0.1 在概要基础上补充的设计决策

| 编号 | 概要中的状态 | 本文的决策 | 理由 |
| --- | --- | --- | --- |
| D1 | 主键写作 `id`，未定类型 | 全表主键改用 **ULID 字符串（26 位）** | 两端各自离线新增数据，自增整数必然撞号，ULID 无中心分配且按时间有序，索引友好 |
| D2 | 库存 = 采购入库 − 销售出库 | 增加 **库存流水表 `stock_ledger`**，类型含采购、销售、采购退货、销售退货、盘点调整、期初 | 只有采购和销售两种来源时，退货、盘亏、期初建账无处记录，实际经营第一天就会卡住 |
| D3 | 零件删除（概要提到"删除记录"同步） | 已产生流水的零件**只能停用，不能删除**；未产生流水的可软删除 | 删掉零件会让历史单据变成孤儿数据，父母误操作的代价太大 |
| D4 | 同步"自动合并数据" | 流水类 append-only 天然免冲突；主数据行级 **后写入者胜（LWW）**，时间相同则 PC 端胜，被覆盖的旧值全部留档到冲突表供人工复核 | 无人工介入的合并必须有确定性规则，同时保证任何覆盖都可追溯 |
| D5 | 未提及登录与鉴权 | PC 端本机登录 + 手机端配对换取长期令牌 | 后端要监听局域网端口，不做鉴权等于同网段任何设备都能改库存，详见第 8.1 节 |
| D6 | 未提及金额精度 | 金额统一以**整数分**存储，前端展示时除 100 | SQLite 的 REAL 做浮点累加会出现 0.01 误差，对账时说不清 |
| D7 | 手机端本地数据范围 | 手机端**不保存全量历史**，只存零件主数据 + 库存快照 + 近 90 天单据 + 未同步队列 | 手机上重算全部历史流水既慢又没必要，快照 + 增量即可正确显示库存 |
| D8 | 概要列有"扫码查询零件（可选）" | **不做扫码功能**，`html5-qrcode` 从技术栈移除 | 使用者确认不需要；零件检索靠编号/名称/拼音首字母 |
| D9 | 概要未定义"离线"的具体含义 | 离线 = **手机与 PC 不在同一网络**（在外、用流量、在别处 WiFi），此时手机端仍可独立开单，回到同一网络后同步 | 见 0.2 与第 6 节 |
| D10 | 未涉及安全上下文问题 | 采用**自签证书方案（原 14.1 方案 B）**，手机端走 HTTPS，Service Worker 生效 | 这是 D9 场景能成立的技术前提，详见第 14 节 |

### 0.2 关于"离线"的定义（已确认）

本设计中的离线**不是指手机完全没有网络**，而是指**手机与 PC 不在同一个局域网**：在外面用移动流量、在供应商那边连别人的 WiFi、或 PC 关机。这些情况下手机连不到 PC 后端，但仍要能：

1. 打开手机端页面（靠 Service Worker 缓存的应用外壳）；
2. 查零件、查库存（靠 IndexedDB 中的本地数据）；
3. 正常开出入库单（写入本地队列）；
4. 回到同一网络后一次性同步。

第 3 点里"手机在外面开的单"要等回家（或 PC 开机、手机连回家里 WiFi）才能同步，这是局域网架构的固有性质，不是缺陷。手机端界面会明确显示待同步条数与上次同步时间。

要让第 1 点成立，浏览器必须允许注册 Service Worker，而它要求页面处于安全上下文（HTTPS 或 localhost），`http://192.168.x.x` 不满足。因此采用自签证书方案，设计见第 14 节。

## 1. 设计目标与约束

### 1.1 设计目标

1. **本地优先**：所有业务操作在本机数据库完成即算成功，不依赖网络与云服务器。
2. **两端可独立经营**：手机端在仓库/送货途中单独开单，PC 端在店里单独管理，互不阻塞。
3. **同步后账目一致**：连上同一局域网并触发同步后，库存、采购、销售数据在两端收敛到同一结果。
4. **面向非技术用户**：操作路径短、字段少、错了能改、数据能备份能恢复。
5. **可平滑升级云端**：数据结构与接口不绑定 SQLite 和局域网，将来换 MySQL、上公网无需重做业务层。

### 1.2 约束条件

- 不购买云服务器，不开发原生 App，手机端走 Web/PWA。
- PC 端为浏览器访问的 Web 系统，后端与 SQLite 可部署在店内 Windows 主机，局域网内可用。
- 数据规模预估：零件 1 万～5 万条，年单据量 2 万～10 万行，SQLite 完全够用。
- 使用者为汽配店实际经营人员，界面文案使用行业口语（如"入库""出库""进价""售价"），不用技术术语。

## 2. 总体架构

### 2.1 架构分层

```
┌──────────────────────────────────────────────────────────────┐
│  手机端（浏览器 / PWA）                PC 端（浏览器）         │
│  Vue3 + Vant + Pinia                Vue3 + Element Plus      │
│  ┌────────────────────┐             ┌────────────────────┐   │
│  │ 页面层  开单/查询   │             │ 页面层  管理/报表   │   │
│  ├────────────────────┤             ├────────────────────┤   │
│  │ 业务服务层（TS）    │             │ 业务服务层（TS）    │   │
│  ├────────────────────┤             ├────────────────────┤   │
│  │ 本地仓储层 Dexie   │             │ HTTP 客户端 Axios  │   │
│  └─────────┬──────────┘             └─────────┬──────────┘   │
│            │ IndexedDB + SW 缓存              │ 127.0.0.1     │
└────────────┼───────────────────────────────────┼─────────────┘
             │                                   │
             │   ┌───────────────────────────────▼───────────┐
             │   │  PC 后端  FastAPI（Python）                │
             └──►│  ┌──────────────────────────────────────┐ │
  局域网 HTTPS   │  │ 路由层 routers                        │ │
  /api/sync/*    │  ├──────────────────────────────────────┤ │
                 │  │ 业务服务层 services（库存/单据/报表） │ │
                 │  ├──────────────────────────────────────┤ │
                 │  │ 同步服务 sync（差异/合并/冲突/日志）  │ │
                 │  ├──────────────────────────────────────┤ │
                 │  │ 数据访问层 SQLAlchemy ORM             │ │
                 │  └──────────────┬───────────────────────┘ │
                 │                 │                          │
                 │        SQLite  autostock.db                │
                 └────────────────────────────────────────────┘
```

### 2.2 关键架构说明

**PC 后端是唯一的数据中心（Hub）。** 概要里画的是两端对等结构，实际实现采用星型：手机端只与 PC 后端同步，不与其它手机直接同步。理由是双向对等合并需要向量时钟，复杂度翻倍，而汽配店场景只有一台 PC 常开，星型足够且逻辑简单可验证。将来加第二台手机，也只是多一个客户端注册到同一 Hub。

**PC 前端不做本地库。** PC 前端与后端在同一台机器上，通过 `127.0.0.1:8756` 通信，后端进程与前端页面同生共死，不存在"PC 前端离线"的场景，所以 PC 端无需 IndexedDB，`pc_database.db` 即 SQLite 文件本身。

**手机端是完整的离线客户端。** 手机端在 IndexedDB 中持有可独立开单所需的全部数据，写入立即成功，同步是后台补偿动作而非前置条件。

### 2.3 部署形态

| 组成 | 部署方式 | 说明 |
| --- | --- | --- |
| PC 后端 | Python 环境运行 FastAPI/uvicorn Web 服务 | HTTPS 监听 `0.0.0.0:8756`；另有 8757 端口仅供 CA 证书下载与跳转（14.2） |
| PC 前端 | 构建为静态文件，由 FastAPI 的 StaticFiles 直接托管 | 访问 `https://127.0.0.1:8756` |
| 手机前端 | 同样由 PC 后端托管，路径 `/m`，构建为 PWA | 手机访问 `https://<PC固定内网IP>:8756/m`，安装到主屏幕后离线可用 |
| 数据库 | SQLite 单文件，位于 `%APPDATA%/AutoStock/autostock.db` | 与程序目录分离，避免升级覆盖数据 |
| 备份 | 同目录 `backups/` 下按日期归档 | 详见第 11 节 |

一次部署、一套 Web 服务、一个数据文件，是这个架构对使用者最重要的性质。

## 4. 数据模型设计

### 4.1 公共字段规范

所有业务表统一携带下列字段，同步机制完全依赖它们，不允许缺省。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | TEXT(26) PK | ULID，两端本地生成，全局唯一且按创建时间有序 |
| `created_at` | TEXT | ISO8601 带时区，记录创建时间 |
| `updated_at` | TEXT | ISO8601 带时区，每次修改刷新，LWW 比较依据 |
| `rev` | INTEGER | Hub 侧写入序号，同步增量拉取的游标（仅 PC 库有值） |
| `version` | INTEGER | 行修改次数，从 1 递增，用于乐观锁与冲突识别 |
| `device_id` | TEXT | 最后写入该行的设备标识 |
| `is_deleted` | INTEGER | 0/1 软删除标记（墓碑），同步删除靠它传播 |
| `sync_status` | TEXT | 仅手机端使用：`pending` / `synced` / `conflict` |

金额字段统一为 `INTEGER`，单位为**分**。数量字段为 `DECIMAL(14,3)`，汽配通常整件计量，保留三位小数以支持按米/公斤销售的密封条、润滑油等。

| `remark` | TEXT | 备注 |

流水表 **append-only**：写错了只能补一条反向流水，不允许 UPDATE 或 DELETE。这条规则是同步免冲突的前提，也是账目可审计的前提。

**`stock_snapshot` 库存快照**（派生表，非真相来源）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `part_id` | TEXT PK | 零件 |
| `quantity` | DECIMAL | 当前库存 |
| `avg_cost` | INTEGER | 移动加权平均成本（分） |
| `last_in_at` | TEXT | 最近入库时间 |
| `last_out_at` | TEXT | 最近出库时间 |
| `calc_rev` | INTEGER | 计算所依据的最大流水 rev，用于校验快照是否过期 |

## 5. 核心业务流程

### 5.1 库存计算规则

概要定义"当前库存 = 采购入库 − 销售出库"，扩充为完整口径：

```
当前库存 = Σ stock_ledger.quantity   （入库为正、出库为负，含期初、退货、盘点调整）
```

各业务动作产生的流水方向：

| 业务动作 | change_type | quantity 方向 |
| --- | --- | --- |
| 采购入库 | `purchase` | + |
| 销售出库 | `sale` | − |
| 采购退货（退还供应商） | `purchase_return` | − |
| 销售退货（客户退回） | `sale_return` | + |
| 盘点盘盈 | `adjust` | + |
| 盘点盘亏 | `adjust` | − |
| 期初建账 | `opening` | + |

成本采用**移动加权平均**：入库时 `新均价 = (原库存×原均价 + 入库量×入库价) / (原库存 + 入库量)`；出库时按当时均价固化到 `sales_item.cost_amount`，此后进价波动不再影响历史毛利。选它而非先进先出，是因为汽配同一零件反复小批量进货，FIFO 的批次跟踪对手工录入负担过重。

### 5.2 采购入库流程

```
选供应商 → 逐行添加零件（编号/名称检索）→ 填数量、进价
   → 前端汇总金额并提示与上次进价的差异
   → 保存
      └─ 后端单事务内：
         1. 校验零件存在且启用、数量>0、进价>=0
         2. 生成单号（CG+日期+设备序列）
         3. 写入 purchase_order 与 purchase_item
         4. 每条明细写入一条 stock_ledger（purchase, +）
         5. 增量更新 stock_snapshot 的 quantity 与 avg_cost
         6. 更新 part.purchase_price 为最新进价（参考值）
         7. change_seq 自增，回填各行 rev
   → 返回单据详情，可打印或继续开单
```

### 5.3 销售出库流程

```
选客户（可跳过=散客）→ 逐行添加零件 → 填数量、售价
   → 前端实时显示可用库存与本行毛利
   → 保存
      └─ 后端单事务内：
         1. 校验库存：可用量 < 出库量时，
            按系统设置 allow_negative_stock 决定"阻止"或"告警放行"
         2. 生成单号（XS+日期+设备序列）
         3. 写入 sales_order 与 sales_item，固化 cost_amount
         4. 每条明细写入 stock_ledger（sale, −）
         5. 更新 stock_snapshot
         6. 更新 part.sale_price 为最新售价（参考值）
         7. change_seq 自增
   → 返回单据详情
```

允许负库存的开关默认**打开但告警**。汽配店常有"货在车上没录入就卖了"的情况，硬性拦截会让人绕过系统记账，比负库存本身危害更大。负库存零件在库存预警页单列一类，提示补录。

### 5.4 撤销与红冲

- **当日、未同步的单据**：允许直接撤销。删除单据与对应流水（同一事务），回滚快照。
- **已同步或跨日的单据**：不允许删除，只能红冲。生成一张类型相同、方向相反的单据，原单标记 `reversed_by`，双方留痕。

界面上这两种情况都叫"作废"，系统内部自动判断走哪条路径，使用者无需理解区别。

### 5.5 盘点流程

```
选盘点范围（全部/按分类/按货位）
  → 系统冻结账面数（记录快照 quantity 与当前 rev）
  → 逐项录入实盘数（PC 表格键盘录入，或手机端按货位逐项录入）
  → 生成差异表：账面数 / 实盘数 / 差异 / 差异金额
  → 确认过账 → 每个差异项写入一条 adjust 流水
```

盘点单本身也是一张单据（`stock_take` 主表 + `stock_take_item` 明细，字段结构同 4.3 惯例），保留完整盘点历史。盘点过程中若发生其它出入库，过账时以"账面数 + 期间变动"重新计算差异，避免误调。

### 5.6 库存预警规则

| 预警类型 | 判定条件 |
| --- | --- |
| 库存不足 | `quantity <= min_stock` 且 `min_stock > 0` |
| 库存积压 | `max_stock` 有值且 `quantity > max_stock` |
| 长期未动销 | `last_out_at` 早于 N 天前（N 默认 180）且 `quantity > 0` |
| 负库存 | `quantity < 0` |

预警在 PC 首页以数字角标呈现，手机端只呈现"库存不足"一类，避免小屏信息过载。

## 6. 多端运行模式

### 6.1 本地独立运行模式

| 端 | 数据位置 | 独立运行时能做 | 不能做 |
| --- | --- | --- | --- |
| PC 端 | `%APPDATA%/AutoStock/autostock.db` | 全部功能 | 无限制 |
| 手机端 | IndexedDB `autostock_mobile` | 零件与库存查询、多明细开单、今日摘要、近 90 天单据详情/预览/分享、客户供应商通讯录 | 完整报表统计、档案批量维护、备份恢复 |

概要 4.1 的例子在本设计下的结果：

```
同步前：
  手机端：零件A 出库 5   → 本地流水 −5，本地快照 = 快照基线 − 5
  PC 端：零件A 入库 100  → 库存 = 原库存 + 100

同步后（两端收敛）：
  零件A 库存 = 原库存 + 100 − 5
```

两笔操作是两条互不相干的流水，合并即相加，不存在"谁覆盖谁"。这就是概要 5 节"不直接同步库存数量，而同步业务流水"的核心价值，本设计完整遵循。

### 6.2 手机端库存显示口径

手机端不保存全量历史流水，库存按下式计算：

```
手机显示库存 = 上次同步得到的 stock_snapshot.quantity
             + 本地所有 sync_status = 'pending' 的流水之和
```

界面上同时标注数据时点，例如"库存 23（含本机未同步 3 笔，数据截至 14:20）"。这句话很重要：让使用者清楚手机上的数字可能不含另一端的最新变动，避免凭手机数字对客户做承诺。

### 6.3 模式切换与状态提示

手机端每 30 秒直接轻量探测 PC 的 `GET /api/health`（超时 2 秒），据此在顶部显示三种状态。此判断不依赖 `navigator.onLine`，因为“能否连接 PC”与“能否访问公网”是两件独立的事：

| 状态 | 展示 | 行为 |
| --- | --- | --- |
| 已连接 | 绿点「已连接 PC」 | 可手动同步；有待同步数据时提示 |
| 离线 | 灰点「离线记账中（待同步 N 笔）」 | 全部写入本地队列 |
| 同步中 | 蓝色进度 | 禁止重复触发 |

探测失败不弹窗、不打断操作，只改变顶部状态，这是"本地优先"在交互层的体现。

## 7. 数据同步设计

### 7.1 同步触发

| 时机 | 说明 |
| --- | --- |
| 手动 | 手机端同步中心点「立即同步」，主路径 |
| 连接恢复 | 探测到 PC 可达且存在待同步数据时，提示一键同步 |
| 应用启动 | 打开手机端且 PC 可达时自动拉取主数据（增量） |
| 定时 | 可选，前台运行期间每 10 分钟一次静默同步 |

概要要求"手动触发同步"为必备路径，自动同步全部作为增强，且任何自动同步失败都不打扰使用者，仅在同步中心留记录。

### 7.2 同步协议

一次同步是「先推后拉」的两次 HTTP 调用，全程幂等，任意步骤失败可整体重试。

**第一步：推送本地变更**

```http
POST /api/sync/push
Authorization: Bearer <device_token>

{
  "device_id": "01J8X...",
  "client_batch_id": "01J9A...",        // 幂等键，重试用同一值
  "changes": [
    {
      "table": "sales_order",
      "op": "upsert",
      "row": { "id": "01J9...", "order_no": "XS20260727M001", ... },
      "client_updated_at": "2026-07-27T14:20:11+08:00"
    },
    { "table": "sales_item",   "op": "upsert", "row": {...} },
    { "table": "stock_ledger", "op": "insert", "row": {...} },
    { "table": "part",         "op": "upsert", "row": {...} }
  ]
}
```

响应：

```json
{
  "batch_id": "01J9A...",
  "accepted": 12,
  "rejected": [ { "id": "01J9...", "reason": "part_not_found" } ],
  "conflicts": [ { "table": "part", "id": "01J9...", "resolution": "remote_win",
                   "server_row": { ... } } ],
  "server_rev": 10432
}
```

**第二步：拉取远端变更**

```http
GET /api/sync/pull?since_rev=10201&limit=500
```

```json
{
  "changes": [ { "table": "part", "op": "upsert", "row": {...}, "rev": 10202 } ],
  "next_rev": 10432,
  "has_more": false,
  "snapshots": [ { "part_id": "01J9...", "quantity": 23, "avg_cost": 4500 } ]
}
```

`has_more` 为真时客户端携带 `next_rev` 继续拉取，直到取尽。分页上限 500 条，保证弱网下单次请求可完成。

### 7.3 冲突判定与解决

| 数据类别 | 涉及表 | 策略 | 说明 |
| --- | --- | --- | --- |
| 流水类（append-only） | `stock_ledger`、`purchase_item`、`sales_item` | **无冲突**，按 `(source_type, source_id)` 或主键 `INSERT OR IGNORE` | 天然幂等，重复推送不会重复记账 |
| 单据主表 | `purchase_order`、`sales_order` | 主键相同则忽略；单号相同但主键不同则重新编号 | 单据一旦生成不做跨端修改 |
| 主数据 | `part`、`brand`、`category`、`supplier`、`customer` | 行级 **LWW**：`updated_at` 大者胜；相等则 PC 端胜 | 覆盖前将败方整行写入 `sync_conflict` |
| 删除 vs 修改 | 全部 | 墓碑与修改按同一 LWW 规则比较 `updated_at` | 删除不特殊化，避免"删除总是赢"导致数据丢失 |
| 库存数量 | `stock_snapshot` | **不同步**，由 Hub 依流水重算后下发 | 派生数据不参与合并，从根上消除库存对不上的可能 |

**时钟偏差处理。** 手机时间可能不准，LWW 依赖时间戳就有风险。因此推送时同时携带 `client_updated_at` 与服务端接收时刻，若二者偏差超过 5 分钟，服务端以接收时刻为准并在冲突表记录 `clock_skew` 标记。配对时校验两端时间差，超过 2 分钟直接提示先校准手机时间。

### 7.4 编号撞车处理

两端离线时可能录入相同 `part_number`，或生成相同 `order_no`（设备序列已尽量避免）。规则：

1. **零件编号相同、主键不同**：判定为同一实物零件被重复建档。以 PC 端记录为主档，手机端那条标记 `merged_into = <PC主键>`，其引用（流水、单据明细）批量改指主档，冲突表留档并在 PC 端提示复核。
2. **单号相同、主键不同**：后到者按 `原单号 + "-2"` 重新编号，业务数据完整保留。

这两种情况都不丢数据、不阻塞同步，只在 PC 端留一条待复核提示。

### 7.5 同步事务与失败恢复

- 服务端处理一个 push 批次使用**单个数据库事务**，要么整批成功要么整批回滚，`client_batch_id` 唯一约束保证重试不重复写入。
- 客户端仅在收到成功响应后，才把对应记录的 `sync_status` 由 `pending` 改为 `synced`；网络中断时状态不变，下次重试。
- 拉取过程中断不影响一致性：游标 `last_pull_rev` 只在整页成功写入本地后才推进。
- 手机端本地写入队列采用 IndexedDB 事务，浏览器被强杀不会留下半条单据。

### 7.6 首次配对与全量初始化

配对全流程（手机需与 PC 在同一网络下完成一次）：

```
①  PC 端 → 设备管理 → 生成配对二维码
       内容：https://192.168.x.x:8756/m?pair=<6位配对码>（5 分钟有效）
②  手机 → 用系统自带相机扫码 → 浏览器打开手机端页面
       （首次会提示证书未受信任，此时按③安装证书）
③  手机 → 按引导页安装 PC 的本地 CA 证书（一次性，约 5 步，详见 14.3）
④  手机 → 重新打开页面，证书已受信任 → 自动提交配对码
⑤  PC 端 → 校验配对码 → 登记 device 记录 → 下发长期令牌 device_token
⑥  手机 → 保存令牌 → 全量拉取：零件档案 + 库存快照 + 近 90 天单据
⑦  手机 → Service Worker 注册并缓存应用外壳
⑧  手机 → 提示"添加到主屏幕"，之后从桌面图标打开
       → 完成，此后脱离该网络也能打开并开单
```

全量初始化按分页拉取并显示进度，1 万条零件在局域网下约 10～20 秒完成。第 ③ 步只在这台手机上做一次，换手机才需重做。第 ⑧ 步很关键：装到主屏幕后打开的是独立窗口，不必每次手输地址，也不会被浏览器标签清理影响缓存。

## 8. 接口设计

### 8.1 鉴权设计

概要未提及鉴权，但后端要监听 `0.0.0.0:8756` 才能让手机访问，这意味着同一局域网（含店里的 WiFi、邻店蹭网、访客手机）内任何设备都能调用接口。若不加鉴权，任何人都能改库存、看进价，因此鉴权是必须项，方案取最轻量的一种：

| 场景 | 方式 |
| --- | --- |
| PC 本机访问 | 启动时输入登录密码（PBKDF2 哈希存 `app_setting`），会话 Cookie 有效期 30 天；来自 `127.0.0.1` 的请求可配置为免登录 |
| 手机端 | 配对时用一次性配对码换取长期 `device_token`（JWT，签名密钥首次启动随机生成并存本地），令牌写入 IndexedDB |
| 令牌吊销 | PC 端设备列表可停用某设备，`is_enabled=0` 后其令牌立即失效（手机丢失时使用） |
| 传输安全 | 局域网 HTTP 明文，进价等信息在同网段可被抓包。可接受性与升级路径见 14.1 |

## 14. HTTPS 与离线运行设计（方案 B，已确认）

### 14.1 为什么需要 HTTPS

手机端要在"不与 PC 同网"的情况下打开页面，唯一途径是浏览器已把应用外壳缓存在本机，这依赖 Service Worker。而 Service Worker 只在安全上下文中可注册：`https://` 或 `localhost`。`http://192.168.x.x:8756/m` 两者都不是，注册会被浏览器直接拒绝，结果是 IndexedDB 里数据都在、页面却打不开。

因此手机端访问必须走 HTTPS。局域网内的 IP 地址无法申请公网证书（Let's Encrypt 要求域名与公网可达），所以采用 PC 自建本地 CA、手机安装一次该 CA 的方式。附带收益是进价、客户等信息不再在局域网内明文传输。

### 14.2 证书生成与服务端配置

PC 后端首次启动时自动完成，无需手工操作：

```
① 生成本地 CA
     AutoStock Local CA，RSA 2048 / ECDSA P-256，有效期 10 年
     私钥存 %APPDATA%/AutoStock/certs/ca.key（仅当前用户可读）
② 探测本机局域网 IP（可能多张网卡，全部纳入）
③ 用 CA 签发服务器证书，有效期 3 年，SAN 包含：
     IP: 192.168.x.x（本机所有内网地址）
     IP: 127.0.0.1
     DNS: localhost
     DNS: autostock.local（预留）
④ uvicorn 以 ssl_certfile / ssl_keyfile 启动，监听 0.0.0.0:8756（HTTPS）
⑤ 另在 8757 端口起一个极小的 HTTP 服务，只做两件事：
     - GET /ca.crt        提供 CA 证书下载（安装证书前必须能用 HTTP 取到）
     - 其它路径 301 跳转到 https://<同一IP>:8756
```

**IP 变动的处理。** 服务器证书的 SAN 绑定了具体 IP，PC 换了 IP 证书就不匹配，且 Service Worker 的缓存是按源（origin）隔离的，源一变缓存就白费。两条措施：

1. 安装时引导在路由器上为 PC 保留固定 IP（DHCP 静态绑定），并建议使用不常见的网段末位（如 `192.168.1.180`），降低与别处 WiFi 撞地址的概率。
2. 后端每次启动检测本机 IP，若发现新 IP 不在现有证书 SAN 内，自动用同一个 CA 重新签发服务器证书。CA 不变，因此**手机上已安装的证书无需重装**，只需在手机端重扫一次配对码更新地址。

**Python 依赖**：`cryptography` 库生成 CA 与证书，不引入 openssl 命令行依赖，减少不同部署环境的额外配置。

### 14.3 Android 手机端证书安装引导

这是整个方案唯一需要使用者动手的地方，做成 PC 端与 Android 手机端的分步引导页，配对时自动进入。

Android（以常见机型为例）：

```
1. 手机扫 PC 上的二维码，浏览器打开 http://192.168.x.x:8757/ca.crt → 下载证书
2. 设置 → 安全 → 加密与凭据 → 安装证书 → CA 证书
3. 选择刚下载的 ca.crt → 确认安装
4. 返回浏览器，打开 https://192.168.x.x:8756/m → 不再提示不安全
5. 浏览器菜单 → 添加到主屏幕
```

引导页提供"安装好了，检测一下"按钮：点击后前端尝试请求 `https://.../api/health`，成功才放行到下一步，避免使用者以为装好了其实没生效。本项目阶段二仅以 Android + Chrome 为目标移动平台，不交付 iOS 证书流程。

**安全边界说明。** 安装这个 CA 意味着该手机会信任由这台 PC 签发的任何证书。CA 私钥仅存在于这台 PC 上、不出网、不进备份包（备份时排除 `certs/` 目录），风险局限于"PC 被入侵后可对该手机做中间人攻击"，对家庭/店铺场景可接受。文档中如实告知，并说明换手机或不再使用时可在手机上删除该证书。

### 14.4 Service Worker 缓存策略

| 资源类别 | 策略 | 说明 |
| --- | --- | --- |
| 应用外壳（HTML/JS/CSS/字体/图标） | Precache + Cache First | 构建时由 Workbox 生成清单，版本号变化才更新 |
| `/api/**` 全部接口 | Network Only | 业务数据一律走 IndexedDB，不缓存接口响应，避免读到过期库存 |
| 导航请求 | Navigation Fallback → `index.html` | 保证任意路径在离线时都能进入应用 |

关键约定：**手机端页面不直接读接口渲染**，一律读 IndexedDB，联网时由同步模块把远端数据写入 IndexedDB。这样"在线"和"离线"在渲染路径上没有分支，不存在只在离线时才暴露的 bug。

PWA manifest：`display: standalone`、`start_url: /m/`、`scope: /m/`，图标 192/512 两档。

### 14.5 离线状态判定

手机端把"能否连到 PC"与"手机有没有网"当作两件独立的事：

| 情况 | `navigator.onLine` | `/api/health` 探测 | 界面状态 |
| --- | --- | --- | --- |
| 在家/店里，同一 WiFi，PC 开着 | true | 成功 | 已连接，可同步 |
| 同一 WiFi，但 PC 关机 | true | 失败 | 离线记账中（PC 未开机） |
| 外面用流量 | true | 失败 | 离线记账中（不在家里网络） |
| 完全无网 | false | 不发起 | 离线记账中 |

后三种在功能上完全等价：写本地队列、显示待同步条数。`navigator.onLine` 为 false 时跳过探测，省电省时。探测超时设 2 秒，失败静默处理，只改顶部状态条。

另一台 WiFi 上恰好存在相同私有 IP 的情况，HTTPS 在这里顺带起了保护作用：对方设备没有我们的证书，TLS 握手直接失败，被当作离线处理，不会把数据推给陌生设备。

### 14.6 分阶段落地

HTTPS 与 Service Worker 提前到**第二阶段**交付，因为"手机在外面也能开单"正是第二阶段手机端的核心价值，缺了它手机端只能在店内用。第二阶段只做本地积压与状态展示，真正的推送/拉取合并留在第三阶段。

### 14.7 其它风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| PC 局域网 IP 变动导致手机连不上，且 SW 缓存按源隔离会失效 | 同步中断、离线缓存作废 | 路由器为 PC 保留固定 IP；后端自动重签证书（CA 不变，手机无需重装）；手机端一键重扫配对码 |
| 手机系统升级后清除用户 CA | HTTPS 报错，离线能力失效 | 配对页保留"重新安装证书"入口，重走 14.3 引导 |
| 浏览器在存储紧张时清理 SW 缓存 | 离线打不开页面 | 引导添加到主屏幕（PWA 安装后优先级更高），并申请持久化存储 `navigator.storage.persist()` |
| PC 未开机时手机无法同步 | 数据积压 | 手机端离线可无限积压，仅提示条数；PC 开机后一次同步完成 |
| Windows 防火墙拦截 8756 端口 | 手机访问失败 | 安装脚本自动添加入站规则，并在设置页提供连通性自检 |
| 数据只在一台 PC 上 | 硬盘损坏则全损 | 备份目录指向 U 盘或网盘同步目录（第 11 节） |
| 手机丢失，本地有进价数据 | 信息泄露 | PC 端吊销该设备令牌；手机端可设打开密码 |
| 使用者误删零件或误录单据 | 账目混乱 | 零件只停用不删除（D3）；单据红冲留痕；每日自动备份 |
| 单据量增长后 SQLite 变慢 | 报表变慢 | 报表按期间分页；必要时增加汇总表，或按概要规划迁移 PostgreSQL |

## 15. 开发阶段与交付物

完全沿用概要第 9 节的三阶段划分，补充每阶段的完成标准。

### 第一阶段：PC 端核心系统

范围：零件/分类/品牌/供应商/客户管理、采购入库、销售出库、退货、盘点、库存查询与预警、Excel 导入导出、统计报表、备份恢复、系统设置。

完成标准：
- 能用真实进货单与销售单完整记账，库存与手工账一致。
- 一致性对账脚本全绿。
- FastAPI 后端与 PC Web 前端可按部署说明启动，浏览器可访问并完成核心业务闭环。
- 附一份图文操作手册（面向使用者，不含技术内容）。

### 第二阶段：手机端系统 + 离线能力

范围：本地 CA 与 HTTPS（14.2）、证书安装引导页（14.3）、扫码配对、手机 Web 访问、IndexedDB 本地库、Service Worker 与 PWA 安装、零件与库存查询、快速入库出库、近期记录、离线状态判定与待同步计数。

完成标准：
- 手机在同一 WiFi 下完成配对与全量初始化，可添加到主屏幕。
- **手机切到移动流量、离开家里网络后，从桌面图标能正常打开应用，能查库存、能开出入库单**，数据进入本地待同步队列并正确计数。
- 手机搜索 1 万条零件响应流畅。
- 同一 WiFi 下开单，PC 端可见（此阶段可先走直连接口写入，不经同步合并流程）。

### 第三阶段：同步系统

范围：push/pull 协议、差异检测、自动合并、冲突记录与复核、同步日志、设备管理与令牌吊销。

完成标准：
- 第 13 节全部同步测试用例通过，含断网重试与重复推送。
- 概要 4.1 场景两端收敛正确。
- 手机在外用流量开 10 单，回到家里 WiFi 后一次同步无差错，PC 端金额与库存核对一致。
- 同步失败对使用者无感知打扰，仅在同步中心可查。
